# x402: paying for API calls under a card's controls

[x402](https://github.com/coinbase/x402) is HTTP's payment-required status put to use: an API answers `402` with a price, the client retries with a signed USDC payment, and the API answers `200` with the resource. It suits per-call machine payments, often fractions of a cent, which card rails handle badly.

A-CARD routes x402 through AFP **under the same controls as a card purchase**. An agent that can buy 500 bags of cement on a card and pay $0.002 for an API call answers to one set of limits, one approval flow and one audit trail.

```
agent ──pay_x402(card, url, max_usd)──▶ A-CARD ──GET url──▶ API
                                          │ ◀── 402 + price ──┘
                     card checks + authorize (limits, approvals, policy, budget, balance)
                                          │ ──GET url + signed USDC payment──▶ API
agent ◀── resource + receipt ─────────────┘ ◀── 200 + settlement ──┘
```

## What gets checked, in order

1. **Before contacting the host** (no network yet):
   - The URL must be HTTPS and resolve only to public addresses. That stops an agent being steered into A-CARD's own network.
   - The card must be active.
   - Its merchant categories must be empty or include `x402`.
   - The host must be in the card's `x402AllowedHosts`, if that's set. An entry like `.example.com` covers subdomains.
2. **The price.** The 402's offers are filtered to USDC, `exact` scheme, on a network the deployment pays on, and the cheapest is chosen. Then:
   - It must be at most the agent's own `max_usd`.
   - It must be within the card's per-transaction limit, compared to the exact amount.
3. **Authorization.** The charge goes through A-CARD's normal `authorize`, merchant `x402 · <host>`, category `x402`. That applies:
   - the card's total and velocity limits;
   - its approval threshold;
   - the org's blocked categories and approval threshold;
   - the department's monthly budget;
   - the wallet balance.

   Over a threshold, the charge is **held** for a person, exactly like a card purchase.
4. **Recorded, then signed.** A pending AFP transaction is written before any signature exists. Then the payment is signed (an EIP-3009 `TransferWithAuthorization`) and sent.
5. **Outcome:**
   - **Paid:** the hold is captured and the transaction is settled.
   - **Refused** by the server: the hold is released and the transaction fails.
   - **Unknown** (dropped connection, a 5xx after the signed payment): the hold stays and the transaction is parked as `reconciling`.

## Prices below a cent: the tab

A-CARD's ledger counts whole cents, and x402 prices are often less than one. Each card keeps a **tab** with two numbers:

- the exact USDC it has paid over x402, in atomic units (millionths of a dollar);
- the whole cents A-CARD has charged the card for it.

A payment only authorizes the cents the tab is about to cross:

| Call | Price | Paid so far | Charged so far | This call charges |
|---|---|---|---|---|
| 1 | $0.001 | $0.001 | 1¢ | **1¢** |
| 2–10 | $0.001 each | $0.010 | 1¢ | 0¢ (credit) |
| 11 | $0.001 | $0.011 | 2¢ | **1¢** |
| — | $2.50 | | | **250¢**, through the full rules, approval threshold included |

The card is never charged less than it has paid, and at most one cent ahead. `GET /v1/afp/x402/tabs/{cardId}` shows the tab.

## Using it

Create a USD card for an agent's API spending:

```bash
curl -X POST "$ACARD_API_URL/v1/cards" -H "authorization: Bearer $ACARD_API_KEY" -H "content-type: application/json" -d '{
  "label": "research-agent API budget",
  "currency": "USD",
  "single_use": false,
  "limits": { "per_transaction": 500, "total": 5000 },
  "allowed_merchant_categories": ["x402"],
  "x402_allowed_hosts": ["api.freight-data.example"],
  "approval_threshold": 200
}'
```

Then pay with it from any surface:

- **MCP:** the `pay_x402` tool, with `{ card_id, url, max_usd: "0.05" }`.
- **SDK:** `await acard.x402.pay({ card_id, url, max_usd: "0.05" })`, then `acard.x402.tab(cardId)`.
- **REST:** `POST /v1/afp/x402/pay` with an `Idempotency-Key` header. See the [API reference](api/reference.md).

A response looks like this:

```json
{
  "status": "paid",
  "price": { "amount_atomic": "25000", "usd": "0.025000", "network": "eip155:84532", "asset": "0x036C…", "pay_to": "0x…" },
  "charged_cents": 3,
  "tab": { "payments": 1, "paid_atomic": "25000", "charged_cents": 3, "credit_atomic": "5000" },
  "settlement": { "success": true, "transaction": "0x…", "network": "eip155:84532" },
  "resource": { "status": 200, "content_type": "application/json", "bytes": 41, "body": "{…}" }
}
```

`status` is one of:

- `paid`
- `free`: the URL didn't ask for payment.
- `held`: approve it in A-CARD, then retry with a new `Idempotency-Key`.
- `declined`: see [decline reasons](reference/errors.md#decline-reasons).
- `failed`: the server refused the payment.
- `reconciling`: the outcome is unknown, and the hold stays.

## Enabling it (operators)

x402 is part of AFP, so `ACARD_ENABLE_AFP=true` comes first.

| Variable | Meaning |
|---|---|
| `ACARD_AFP_X402_PAYER_ADDRESS` | Turns x402 on with the **sandbox signer**. Signatures are syntactically valid and cryptographically meaningless, so no value moves. |
| `ACARD_AFP_X402_SIGNER_KEY` | A secp256k1 key (hex) for a **real** signer. It only starts together with `ACARD_AFP_X402_REAL_VALUE=true`; a key without that flag refuses to boot. The payer address is derived from the key. |
| `ACARD_AFP_X402_REAL_VALUE` | `true` to allow the real signer above. |
| `ACARD_AFP_X402_NETWORKS` | Comma-separated CAIP-2 networks to pay on. Default `eip155:84532` (Base Sepolia, testnet). Base mainnet (`eip155:8453`) must be listed explicitly. |
| `ACARD_AFP_X402_ALLOW_PRIVATE_NETWORKS` | Sandbox only: allow plain HTTP and private addresses, for a local test server. Refused together with a real key. |

With a real signer, the x402 rail reports `carriesRealValue`, so the crypto-compliance layer (Travel Rule, wallet screening) mounts by itself.

**Custody.** The real signer holds a raw key in process memory. That suits a testnet float or a small hot wallet that the org tops up. Anything larger belongs in a KMS or a custody provider (Circle, Fireblocks), implementing the same `X402Signer` interface in `apps/api/src/x402/signer.ts`. The float is the org's USDC. The tab moves the org's fiat ledger by the same amount, to the cent.

## Wire format

Both versions in the field are supported. The details are in `apps/api/src/x402/protocol.ts`.

| | v2 (spec checked Oct 2026) | v1 |
|---|---|---|
| Price, server → client | `PAYMENT-REQUIRED` header, base64 JSON, `amount` | 402 JSON body, `maxAmountRequired` |
| Payment, client → server | `PAYMENT-SIGNATURE`, which echoes the chosen requirement as `accepted` | `X-PAYMENT` |
| Settlement, server → client | `PAYMENT-RESPONSE` | `X-PAYMENT-RESPONSE` |
| Networks | CAIP-2 (`eip155:8453`) | names (`base`, `base-sepolia`) |

The signer produces the EIP-712 `TransferWithAuthorization` signature the `exact` EVM scheme uses. A test checks it byte for byte against viem's independent implementation.

## Limits of this version

- **USDC on Base and Base Sepolia, `exact` scheme, EIP-3009 only.** Permit2 and ERC-7710 transfers, other tokens and other chains are skipped as unsupported, not attempted.
- **The tab's credit is protected per API instance.** Two instances paying on the same card at the same instant could both spend the same sub-cent credit, so the card would be charged up to one cent less than it paid. Limits, approvals and balance are unaffected: they are enforced by the authorization itself, which is multi-writer safe.
- **The URL check happens before the request.** A hostname that resolves to a public address when checked and a private one a moment later (DNS rebinding) isn't caught. Redirects are never followed.
- **Not yet live.** Like the rest of A-CARD, this runs in the sandbox until launch. Moving real USDC also needs the custody decision above.
